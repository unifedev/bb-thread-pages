# 01 — The page model

## Ownership

Every page has exactly one **owner**: the agent session it belongs to. Ownership
is identity, not permission — the page's URL, its storage location and its
capability scope all derive from the owner's session id.

An agent MUST be able to read and write its own page. An agent MUST NOT be given
a mechanism to read or write another agent's page. This is not enforced by file
permissions (the agent has a shell and owns the machine); it is enforced by *not
providing the mechanism* and by saying so in the standing instruction (P1, P5).

### Eligibility

Not every session may own a page. A session is **eligible** when it is:

- **visible** — not an internal helper the reader never sees;
- **a root** — not a child of another session, and not a fork of one;
- **live** — not archived and not deleted.

An ineligible session MUST be told plainly that it has no page and MUST NOT be
given one. The reason is that a page is a conversation surface with the reader; a
sub-agent spawned for a subtask has no such relationship.

Hosts MAY define eligibility differently if their session model differs, but MUST
define it, and MUST make the answer available to the agent — see the `init`
subcommand in [06-agent-contract.md](./06-agent-contract.md).

## Lifecycle

1. **Initialisation.** The agent asks for its page. If none exists, the host
   creates one from the configured seed. If one exists, the host reports that and
   changes nothing.
2. **Authoring.** The agent edits the file with ordinary file tools.
3. **Publication.** Saving the file publishes it. The host MUST detect the change
   without being told.
4. **Reading.** The reader opens the URL. An already-open page MUST update itself
   when the file changes, subject to the update protection in
   [02-serving.md](./02-serving.md).
5. **End.** A page persists as long as its owner session does. When a session is
   archived or deleted, its page stops being served.

There is no revision history, no draft state, and no rollback. The file is the
page (P1).

### The agent is not obliged to rewrite

The standing instruction tells an agent to keep its page current, which for most
tasks means rewriting it each turn. This is guidance about *what a page is for*,
not a lifecycle rule. An agent that has finished, or that built a durable surface
intended to stay put, leaves its page alone.

An implementation MUST NOT regenerate, reset, or garbage-collect a page on the
agent's behalf.

## Storage

A page's storage is a **directory owned by that page**:

```
<page-root>/
  index.html          the page's entry document
  <any files>         stylesheets, scripts, images, fonts, data
  <any directories>   nested as the agent likes
  uploads/            files the reader attached (host-managed)
```

Requirements:

- **R1.1** The entry document MUST be at a fixed, documented path within the
  page root. A request for the page's URL serves that document.
- **R1.2** The page root MUST be served as a **site**: any file within it is
  reachable at its path relative to the page's own URL, with nested directories
  preserved.
- **R1.3** Relative references inside the entry document (`href="style.css"`,
  `src="img/logo.png"`) MUST resolve against the page's own URL. The host MUST
  NOT rewrite the document to point elsewhere, and MUST NOT inject a `<base>`
  element pointing at a different origin.
- **R1.4** Path traversal MUST be refused. A request that resolves outside the
  page root MUST fail, whether by `..`, an absolute path, a symbolic link, or
  URL encoding.
- **R1.5** Symbolic links pointing outside the page root MUST NOT be followed.
  A host MAY refuse them entirely.
- **R1.6** The uploads directory is host-managed. Filenames within it are
  generated by the host, never taken from the reader
  ([04-page-runtime.md](./04-page-runtime.md) §Uploads).

### Why a site and not a flat asset list

*Rationale, informative.* P3 states a page may grow into a site of several files.
A flat directory served from a separate origin cannot express that: it forbids
nested paths, and it makes every relative reference depend on an injected base
pointing somewhere else. Serving the page's own directory under the page's own
URL is the only shape that satisfies R1.2 and R1.3 together, and it removes two
classes of bug the previous design had — see
[09-conformance.md](./09-conformance.md).

### Size

- **R1.7** The entry document MUST be bounded. Recommended limit: 5 MiB. A
  document above the limit MUST be refused with a message naming the limit, and
  MUST NOT be silently truncated.
- **R1.8** Other files in the page root SHOULD be bounded per-file and MAY be
  bounded in total. A host MUST document its limits.
- **R1.9** Neither the page root nor the uploads directory is pruned
  automatically. A host SHOULD provide a way to report and reclaim space.

## Multi-file pages

A page MAY consist of several files. This is a normal case, not an advanced one.

- **R1.10** The agent needs no permission and no declaration to add files. It
  writes them into its page root.
- **R1.11** Filenames and directory names within a page root MUST NOT be
  restricted beyond what the filesystem and R1.4/R1.5 require. Restricting the
  character set (as the previous design did) is a violation of P1: an author
  should be able to name a file what they would name it anywhere.
- **R1.12** A host MUST serve a correct `Content-Type` for common web types by
  extension, and MUST NOT execute anything server-side. Everything in a page root
  is a static file.

## Identity and URLs

- **R1.13** A page's URL MUST be stable for the life of its owner session, and
  MUST be derivable from the session id alone.
- **R1.14** The URL MUST be on the same origin the reader authenticates to, so
  that no additional port, tunnel or credential is needed (P2, and goal 4 in
  [00-product.md](./00-product.md)).
- **R1.15** A page's URL MUST NOT encode a secret. Authority to *read* comes from
  the reader's existing session with the host; authority to *act* is separate and
  specified in [02-serving.md](./02-serving.md).

## Durable surfaces

A durable surface is a page whose forms start fresh agents rather than messaging
its owner. There is no additional mechanism, and an implementation MUST NOT add
one.

Requirements that make it work:

- **R1.16** Starting a session from a page MUST be possible and MUST succeed
  without the page having to know host-specific details
  ([05-capabilities.md](./05-capabilities.md) §`sessions.start`).
- **R1.17** A page whose owner is idle MUST continue to be served, and MUST
  remain fully interactive. An idle owner is the normal state of a durable
  surface, not a fault.
- **R1.18** The standing instruction MUST teach the composition route: to create
  another interface, start an agent and ask it for one
  ([06-agent-contract.md](./06-agent-contract.md)).

### Anti-pattern, stated so it is not repeated

An owner-less page — a session created solely to hold a page, with no agent ever
running in it — is **not** the way to build a durable surface. It produces
sessions in a permanently odd state and a page nobody can maintain. A durable
surface MUST be owned by a real agent that built it and then stopped (P3).
