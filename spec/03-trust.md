# 03 — Trust boundary

## What is being defended

Page code is generated by a language model. It is not reviewed before it runs, so
it is treated as code the operator did not write.

The thing being defended is **the host's authority**: the ability to act as the
reader, change sessions, read arbitrary files, or reach services that trust the
host's identity. That is what a page must never hold.

The thing **not** being defended is the page's ability to compute, render, or
reach the public network. Attempting that defence was tried and abandoned; §Network
explains why it never worked.

## The three layers

### Inside the frame — untrusted

The document runs in an iframe with a sandbox that gives it script execution and
form semantics and nothing else, on an **opaque origin**.

- **R3.1** The document MUST NOT have access to: the host's session cookie, any
  mutation or CSRF token, the shell's DOM, `localStorage`/`sessionStorage` shared
  with the host origin, the host's API, a shell or filesystem, or any credential.
- **R3.2** The document's origin MUST be opaque, so it is same-origin with
  nothing — including other pages from the same host.
- **R3.3** The sandbox MUST NOT grant top-level navigation, popups, or modal
  dialogs. Consequences are specified in
  [04-page-runtime.md](./04-page-runtime.md) §Unavailable browser affordances.
- **R3.4** Arbitrary HTML, CSS and JavaScript MUST be permitted, including
  frameworks, Web Components, canvas, WebGL, workers and audio. This is the
  product; restricting it is out of scope for security because R3.1 already
  removes the authority that would make creativity dangerous.

### The shell — trusted

- **R3.5** The shell is host-authored. It holds the action token, makes the
  same-origin requests, owns navigation, and renders confirmations.
- **R3.6** The shell MUST NOT execute anything supplied by the page: no page-
  authored HTML, no page-authored script, no page-supplied dialog text.
- **R3.7** The shell MUST verify the origin and identity of messages it accepts
  from the frame, and MUST ignore anything else.

### Between them — one narrow channel

- **R3.8** Exactly one `MessagePort`, established by the shell, handed to the
  document once at load.
- **R3.9** Every message MUST be validated against a fixed schema before use.
- **R3.10** There MUST be no generic "call the host" method, no path or endpoint
  parameter, and no pass-through to a provider or SDK. Each capability is named
  and validated individually ([05-capabilities.md](./05-capabilities.md)).

## Network access

**Pages have internet access.** `connect-src` and subresource loading are open:
a page MAY fetch data, load fonts, scripts, stylesheets, images and media from
any origin, and MAY open WebSockets.

This reverses an earlier design that blocked it. The reasoning is recorded in
full in [../docs/DECISIONS.md](../docs/DECISIONS.md) D7; the operative points:

1. **It never prevented exfiltration.** Page JavaScript can navigate its own
   frame and encode frame-local data in the destination URL. No sandbox flag and
   no CSP resource directive closes that channel. So blocking `connect-src`
   bought obscurity, not containment — and a limit that one line of code walks
   around is not a limit.
2. **The threat it implied does not exist here.** The agent that wrote the page
   already has the machine and can act directly; a remote script the agent chose
   to include is one it could have used anywhere; local programs can already
   start agents.
3. **The cost was most of the product.** Fonts, images, data, maps and libraries
   are what make a page an application rather than a document.
4. **The surface is authenticated and single-owner** (P5).

Requirements:

- **R3.11** The document's CSP MUST permit outbound connections and subresource
  loads from any origin.
- **R3.12** Opening the network MUST NOT relax anything in R3.1. Reaching a URL
  and holding the host's authority are different things; only the first is open.
- **R3.13** A page MUST be able to read its own files as data (`fetch` of a
  relative path).

  This does **not** follow from R3.11 and R1.2 alone, and is easy to get wrong. A
  sandboxed document on an opaque origin is same-origin with nothing, so a
  `fetch` of its *own* file is a **cross-origin request carrying `Origin: null`**.
  The route serving a page's files MUST answer such a request with
  `Access-Control-Allow-Origin: null`.

  Otherwise the fetch fails while the identical URL loads perfectly well as a
  subresource — measured in the reference implementation, whose file route
  answers `403` to `Origin: null`. Subresource loading is unaffected either way,
  which is exactly what makes this inconsistency hard to spot.

### The reader's network — accepted consequence

A page runs in the **reader's** browser, which is frequently not the host's
machine: a phone on home wifi, a laptop in an office.

With an open `connect-src`, page script can reach whatever that device can
reach — including its loopback interface and private-range addresses. This does
**not** follow from "the agent already owns the host", because it is a different
machine.

- **R3.14** This is **accepted**, explicitly, by the product owner.
- **R3.15** A host MUST NOT attempt to prevent it with a curated allow-list. CSP
  cannot express "public internet but not private ranges", so the only mechanism
  is an allow-list, which contradicts the decision above.
- **R3.16** A host MUST state this consequence in its security documentation so
  it is a known property rather than a surprise.

## Confirmed effects

Anything reaching outside the page's own session requires a confirmation the page
cannot fake, word, or skip.

- **R3.17** The flow MUST be: page invokes → host refuses once, returning a
  **signed challenge carrying the host's own summary** → shell displays that
  summary → shell returns the challenge → host verifies the signature and acts.
- **R3.18** The summary MUST be derived by the host from validated parameters.
  The page MUST NOT supply it, and MUST NOT see the challenge before the shell
  does.
- **R3.19** The challenge MUST be bound to: one request id, the method, a
  fingerprint of the exact parameters, the page revision, and the session. It
  MUST expire quickly. Recommended: 2 minutes.
- **R3.20** Parameter binding MUST use a canonical serialisation, so that
  reordering keys cannot change the fingerprint.
- **R3.21** A declined confirmation MUST reject the call with a distinguishable
  `cancelled` code. A page MUST be able to tell "declined" from "failed".
- **R3.22** The dialog MUST be rendered in chrome the sandboxed page cannot draw
  over, click, or reword.

*This closes the specific attack of getting "message session A" approved and
reusing the approval for session B.*

## The honest limitation

- **R3.23** Page JavaScript can navigate its own frame and encode data in the
  URL. It therefore has access to data already inside its frame. This MUST be
  documented, not implied.

Closing it entirely would require forbidding authored JavaScript and shipping a
declarative renderer instead — which would cost the open-page model that is the
product. This is a stated trade.

It is also the reason the network restriction was dropped rather than defended:
the channel was already open, so the restriction was theatre.

## What a hostile page can and cannot do

Normative summary. An implementation SHOULD have a test for each row.

| A hostile page tries to… | Result |
| --- | --- |
| Read the host's session cookie | Impossible: opaque origin, no cookie in frame |
| Read the action token | Impossible: held by the shell only |
| Reach the shell's DOM or `window.top` | Blocked by the sandbox; throws |
| Navigate the top window | Blocked by the sandbox |
| Call the host API directly | No credential; requests are unauthenticated |
| Forge a capability call for another session | Rejected: the token names its own session |
| Forge or replay a confirmation | Rejected: signed, parameter-bound, short-lived |
| Reword a confirmation dialog | Impossible: the host authors the summary |
| Reuse an approval for different parameters | Rejected: parameter fingerprint mismatch |
| Read another page's stored state | Rejected: storage is namespaced per session |
| Read a real filesystem path from the folder picker | Impossible: an opaque token is returned |
| Act on a page revision that has changed | Rejected: stale-page error |
| Exhaust the host with calls | Bounded: per-page rate limit |
| Send frame-local data to a remote server | **Possible, and accepted** (R3.11, R3.23) |
| Reach the reader's private network | **Possible, and accepted** (R3.14) |

## Threat model boundaries

Out of scope, stated so nobody assumes otherwise:

- **A malicious operator.** Whoever runs the host can read everything.
- **A malicious agent with shell access.** The agent already owns the machine.
  Page sandboxing protects the reader's *browser session*, not the machine.
- **Multi-tenant use.** This spec assumes one owner. Serving pages from one host
  to mutually untrusting readers is not specified and MUST NOT be assumed safe.
- **Data already visible to the page** (R3.23).
